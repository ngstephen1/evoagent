What worked — member-confirmed scale fixer (+0.44pt). 8 tightly-gated percent→ratio fixes (phase3_scale_fix.py → v2) took Kaggle 0.694 → 0.69838. A row was changed only when a ratio/percent question had value > 1.5 and some member model had already produced the ÷100 form. The gold convention is a decimal ratio (dev: median |ans| = 0.375; 71% ≤ 1.0), and the metric uses a tight absolute tolerance (abs(pred − gold) ≤ 1e-4), so a 100× scale error is always fatal.
What failed — blind scale fixer (−1.6pt). v3 divided 36 more rows by 100 on question wording alone (no member confirmed the ratio form) and dropped to 0.68218. Lesson: when all three models agree on the big value, the big value is usually correct. The member-confirmation gate was the real signal, not the wording. Post-processing is now exhausted — further gains need better predictions, not more patching. v2 is frozen as the floor.

Improvement plan

Done — local validation harness (phase3_dev_eval.py). Scores predictions against the labeled dev set (584 rows) using the project's own metric, sliced by source / complexity / table-lookup / ratio-Q. Self-test on gold programs = 100%, so local scoring is trustworthy. This ends the blind Kaggle probing that cost us on v3 — every future change gets a local number first.

Next lever — expand the ensemble recommended

Post-processing is tapped out; the lever that actually moved the score historically was ensemble diversity (Coder-7B scored 0.48 alone yet lifted the ensemble). Cheapest reliable path, on Modal (A10G inference, ~$1/hr):

  1. Pick a diverse ≤9B model from a different family (e.g. Llama / Mistral / DeepSeek-Math).
  2. Run it over both dev.json and test.json via run_modal.py's SGLang path.
  3. Score its dev output with phase3_dev_eval.py to confirm it is a useful voter.
  4. Generate dev predictions for the existing 3 members once, build the vote on dev, and score locally — pick the config (3-way vs 5-way, with / without scale-fix) that wins on dev before submitting.
  5. Submit the winner; keep v2 (0.69838) as the floor.

Realistic ceiling for expanded voting: ~0.70–0.72.

Stretch lever — LoRA fine-tune

Highest ceiling, highest cost — do it only if ensemble expansion plateaus. Fine-tune Qwen3-8B on train.json's 2,986 gold programs (output the DSL program, auto-verifiable via evaluator.py; over-sample scale / sign / table cases). Needs a bigger GPU (A100/H100) and the harness to tune against. Natural follow-on: rejection sampling — sample N programs per train question, keep those that execute to exe_ans, and SFT on the survivors.

Sequence: validation harness (done) → expand ensemble on Modal (measure on dev, then submit) → LoRA only if plateaued. Guardrail: every change is scored on dev before a Kaggle submission, and v2 stays the frozen floor.
